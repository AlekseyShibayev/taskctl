# Как писать спеку

## 1. Спека и соседние документы

| Документ | Отвечает на вопрос | Меняется |
|---|---|---|
| `SPEC.md` | Что должно быть верно, в каких границах и как это проверить | С каждым изменением контракта, тем же PR, что и код |
| `README.md` | Как поставить, запустить, чем пользоваться | При изменении установки, CLI, конфигурации |
| ADR | Почему выбрано именно это решение и что отвергнуто | Никогда; устаревший помечается `superseded` |
| Задача в трекере | Кто делает, когда, что осталось | В ходе работы |

Спека — контракт и критерии приёмки. Не инструкция (README), не история решения (ADR), не план работ (тикет).
Один факт живёт в одном документе, остальные ссылаются.

## 2. Шаблон

```markdown
# SPEC — <компонент>

| Поле | Значение |
|---|---|
| Статус | draft / accepted / superseded |
| Версия | 1 |
| Дата | 2026-11-16 |
| Код | internal/store, internal/mcp |

## 1. Контекст и цель
Где работает, для кого, какую проблему решает. 3–5 предложений, без истории проекта.

## 2. Границы
**In scope:** что входит.
**Out of scope:** что осознанно не делаем. Пункт обязателен.

## 3. Поведение и сценарии
По абзацу на операцию: вход, выход, порядок, побочные эффекты.
Сюда же — что считается успехом, пустым результатом и ошибкой.

## 4. Инварианты и гарантии
| ID | Утверждение |
|----|-------------|
| INV-1 | ... |

Инвариант — то, что верно при любом порядке вызовов, включая параллельные и после перезапуска.

## 5. Данные и ошибки
Схема, форматы, лимиты, точные тексты ошибок, коды.

## 6. Критерии приёмки
| ID | Проверка | Тест |
|----|----------|------|
| ACC-1 | ... | TestX |

Проверка формулируется так, чтобы её мог выполнить человек без чтения кода.

## 7. Открытые вопросы
Вопрос — кто отвечает — к какому сроку. Нет вопросов — так и написать.

## 8. Ссылки
Код, тесты, ADR, внешние стандарты. Ссылки на файлы, а не на «где-то обсуждали».
```

## 3. Правила

- **Проверяемость.** Каждое требование можно проверить тестом, командой или чтением лога. «Удобно», «надёжно», «быстро» — не требования.
- **Что, а не как.** Реализация попадает в спеку только тогда, когда она сама часть контракта (атомарность, один запрос, порядок выдачи) — и тогда формулируется как гарантия, а не как инструкция программисту.
- **Числа вместо прилагательных.** «Много» → «≤ 1 MiB», «быстро» → «p95 < 50 мс на 10⁵ строк», «редко» → «не чаще 1 раза в сутки».
- **Один факт в одном месте.** Дублирование факта — это будущее расхождение.
- **Рядом с кодом.** Спека лежит в модуле (`taskctl/SPEC.md`) и меняется тем же PR, что и код. Изменение контракта без правки спеки — незавершённая работа.
- **Не дублирует код и тесты.** Не вставлять тела функций и не пересказывать тесты; фиксировать наблюдаемое поведение, формат, лимиты, не-цели. Вместо копии — ссылка на файл и имя теста.
- **Не-цели обязательны.** Без `Out of scope` объём расползается: каждая не названная функция считается обещанной.
- **ID вместо абзацев.** `INV-1`, `ACC-3` — на них ссылаются тесты, коммиты и ревью.

## 4. Антипаттерны

| Антипаттерн | Признак | Что делать |
|---|---|---|
| Спека-роман | Больше 2 страниц, история решений, рассуждения «а что если» | Контракт оставить, историю — в ADR, установку — в README |
| Спека-пожелание | «Должно быть удобно», «желательно быстро», «по возможности» | Заменить проверяемым утверждением или удалить |
| Спека без не-целей | Есть только «что делаем» | Добавить `Out of scope`; молчание = обещание |
| Расхождение с кодом | Спека обещает одно, тест проверяет другое | Править в одном PR; при споре решает код, спека догоняет |
| Спека-копия кода | Переписанные функции, схемы «на будущее» | Оставить контракт и ссылки |
| Спека-вечная | Нет статуса, старые разделы не удаляются | Статус `superseded` + ссылка на замену |

## 5. Чек-лист ревью спеки

1. Есть статус, версия, дата.
2. Цель сформулирована за 3–5 предложений, без предыстории.
3. `Out of scope` непустой и честный.
4. Каждое требование проверяемо без чтения кода.
5. Прилагательные заменены числами и границами.
6. Инварианты пронумерованы и покрывают параллельность и перезапуск.
7. Форматы данных и ошибок заданы буквально: пример JSON, точный текст ошибки.
8. У каждого критерия приёмки есть тест или команда.
9. Нет фактов, продублированных из README/ADR/кода.
10. Спека и код в одном PR, ссылки живые.

## 6. Пример: одна страница для taskctl

````markdown
# SPEC — taskctl: очередь create/get

| Поле | Значение |
|---|---|
| Статус | accepted |
| Версия | 2 |
| Дата | 2026-11-16 |
| Код | internal/store, internal/mcp, cmd/taskctl |

## 1. Контекст и цель
MCP-сервер по stdio, задачи в локальной SQLite, без сети. Одна команда —
`taskctl mcp`. Цель: задача, положенная один раз, выдаётся не более одного раза
при параллельных вызовах и перезапусках.

## 2. Границы
**In scope:** `create(text)`, `get()`, схема `tasks`, путь к БД, отказ от чужой схемы.
**Out of scope:** сеть; статусы и переходы; lease, таймауты, возврат задачи в очередь;
удаление и редактирование; список и пагинация; миграции; macOS/Windows.

## 3. Поведение
`create(text)` — `text` обязателен, непустой после TrimSpace, ≤ 1 048 576 байт,
валидный UTF-8. Возвращает задачу с `get_at: null`. `id` монотонно растёт.

`get()` — без аргументов. Берёт задачу с минимальным `id` среди `get_at IS NULL`,
проставляет `get_at = now` (UTC) и возвращает её. Порядок выдачи = порядок создания.
Выбор и запись — один `UPDATE ... RETURNING`; отдельного `SELECT` нет.

## 4. Инварианты
| ID | Утверждение |
|----|-------------|
| INV-1 | Взятая задача не выдаётся повторно: ни этим процессом, ни другим, ни после перезапуска. |
| INV-2 | N параллельных `get` на M свободных задачах дают min(N, M) разных `id`; остальные получают ошибку пустой очереди. |
| INV-3 | `create` не меняет `get_at`; `get` не меняет `text` и `create_at`. |
| INV-4 | `get` на пустой очереди — ошибка (`isError: true`), не `null`. |
| INV-5 | `create` вернул `id` — строка закоммичена и видна следующему `get`. |
| INV-6 | База со схемой, отличной от `[id, text, create_at, get_at]`, не открывается; миграции нет. |

## 5. Данные и ошибки
```sql
CREATE TABLE IF NOT EXISTS tasks (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  text      TEXT NOT NULL,
  create_at TEXT NOT NULL,
  get_at    TEXT NULL
);
CREATE INDEX IF NOT EXISTS tasks_unclaimed ON tasks (id) WHERE get_at IS NULL;
```

Ответ — JSON в `content[0].text`; время RFC3339, UTC, до секунды:
`{"id": 1, "text": "...", "create_at": "2026-11-16T12:00:00Z", "get_at": null}`

Ошибки инструмента: `isError: true`, текст в `content[0].text`. JSON-RPC error
для бизнес-ошибок не используется. Тексты:
`text is required` · `text must not be empty` · `text must be at most 1048576 bytes`
· `text must be valid UTF-8` · `queue is empty: every task has been taken` ·
`invalid arguments: <причина>` · `... has an incompatible schema: columns [...], want [...]`.

## 6. Критерии приёмки
| ID | Проверка | Тест |
|----|----------|------|
| ACC-1 | `create` → `get`: тот же `id` и `text`, `get_at` заполнен, UTC до секунды | TestCreateAndGet |
| ACC-2 | Второй `get` на единственной задаче → ошибка пустой очереди | TestGetTakesEachTaskOnce |
| ACC-3 | 40 `get` из двух `Store` на 20 задачах → 20 разных `id`, остальные `ErrEmpty` | TestTakeIsAtomic |
| ACC-4 | `get` на пустой БД → `isError: true` | TestTakeOldestUnclaimed |
| ACC-5 | Пустой и пробельный `text` — ошибка без записи; ровно 1 MiB — успех | TestAddValidation |
| ACC-6 | База со старыми колонками → `incompatible schema` | TestIncompatibleSchemaRejected |
| ACC-7 | Перезапуск: взятая задача не выдаётся | TestTakeSkipsClaimed |

## 7. Открытые вопросы
Очистка старых взятых задач — не решена, вне версии 2. Владелец: автор модуля.

## 8. Ссылки
`internal/store/store.go` · `internal/mcp/tools.go` · `internal/store/store_test.go`
````

Что в примере сделано по правилам: числа вместо «большой»/«быстрый», `Out of scope`
перечислен, инварианты отделены от сценариев, ошибки заданы точными строками,
каждый критерий приёмки ссылается на существующий тест.

Рабочая версия этой же спеки — `taskctl/SPEC.md`; пример выше и она меняются
одним PR. Расхождение спеки с кодом чинится правкой спеки, а не исключением.
